# 我的大学日记（CampusMock）开发规划

> 当前仅规划文档，尚未实现。已确认玩法以 README 和游戏规则为准；本文记录面向 4 人、5 天 MVP 的实现设计及已确认的成员分工和开发节奏。具体模型尚未实测，演示时长按要求暂缓。

## 一、首版交付范围

React + Vite + Express + TypeScript；14 天、每天 1 个事件；初始学业 0、社交 0、精力 7、金钱 1000。模型结合天数、属性和历史生成事件、选项及量化效果；第 14 次结算后，按四维各自的 A～D 档位生成结局。

产品展示名确定为“我的大学日记”。界面围绕每日关键片段和日记回顾组织，整体采用心理治愈风格。游玩过程中仅展示精力与金钱，学业和社交在后台参与生成、结算和结局。

首版功能范围按上述需求冻结，包含浏览器存档与恢复、失败重试、本机及局域网访问。分档与变化范围见 [游戏规则](游戏规则.md)。不增加账号、云端同步、多人、额外支线、地图、语音、图片生成或复杂 Agent 系统。

## 二、AI 调研与已确认调用方式

### 接口事实

- DeepSeek 提供兼容 OpenAI 格式的 API，可通过服务端配置地址、密钥和模型调用。[首次调用 API](https://api-docs.deepseek.com/zh-cn/)
- Chat Completions 支持 JSON 输出；后端仍需验证必填字段、属性类型和单次变化范围。[接口文档](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)
- Chat Completions 不自动保存跨请求的历史，应用必须提供所需上下文。[多轮对话说明](https://api-docs.deepseek.com/guides/multi_round_chat/)

目前仅完成文档调研，尚未验证账号可用模型、响应耗时、费用及失败率。模型名称与请求超时通过后端配置管理，接入时选择并验证，不在业务代码中固定供应商版本。

### 正常一局约 15 次模型调用

| 时机 | 输入 | 一次调用的输出 | 次数 |
| --- | --- | --- | --- |
| 每天生成事件 | 游戏天数、当前四维值、过往事件及选择 | 事件标题、详情、选项、各选项的四维变化及简短结果叙述 | 14 |
| 两周结束 | 最终四维值、四个档位与本局经历 | 结局标题、详情、评价与建议 | 1 |

事件生成与选项量化合并调用。玩家选择后直接使用已固定的数值与结果叙述结算，不再调用模型。结局独立调用，失败时只重试结局。上述次数不包含失败重试；浏览器尚未保存的生成响应在中断后可能需要重新请求。

### 事件多样性与后续影响

提示词明确“大学新生、入学两周、期待与焦虑、心理治愈”的主题边界，根据当天天数和属性生成情境，不建立每天必触发的固定事件表。文案需要温和、真诚并包含可信的校园细节，避免纯搞怪、标签化评价和单一正确选项。

保留已有事件、玩家选择、结果和数值变化，让模型能延续人物、约定和经历。首版仅有 14 个事件，使用有长度限制的文字记录；每次构建简洁上下文，不额外调用模型做摘要，也不引入向量数据库。

同一游戏天数，低精力与高精力状态应能产生不同情境；此前选择过协商或回避，也应在后续描述或选项中产生可解释的影响。仅把事件的形容词换一遍不满足多样性验收。

## 三、存档与恢复设计

### localStorage 方案

采用用户提出的 localStorage 方向作为 MVP 实现方案：浏览器保存完整单局快照，Express 接口读取并校验请求中携带的快照，不依赖只存在于服务内存中的会话。后端负责规则校验和结算，浏览器负责持久保存返回的完整状态。

快照包含规则版本、存档版本、游戏标识、状态修订号、当前阶段、四维值、已完成历史、当前未结算事件及其全部选项效果、已生成结局。只保存一个游戏标识或四个数值不足以恢复。

localStorage 的数据可跨浏览器会话保存，并按访问源隔离；浏览器设置也可能阻止写入。因而服务重启后的恢复需要保持原访问源，且依赖站点数据仍然存在。[localStorage 说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

- 同一浏览器访问相同协议、主机、端口，可恢复已成功保存的状态。
- localhost、127.0.0.1、局域网 IP 和不同端口分别使用不同存档；其他设备不共享该存档。
- 浏览器清理站点数据、隐私模式结束或禁止持久存储不属于可保证的恢复场景。
- 存档采用单个 JSON 快照，仅在事件生成、选项结算、推进或结局保存时写入，不逐字写入模型输出。
- 建议将单局序列化文本控制在 200 KB 以内作为内部目标，并实测字节数。存储配额不能只靠估算保证，需捕获写入异常。[存储配额与异常说明](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

该方案面向单人本地体验。后端可以检查结构与结算一致性，但仅凭浏览器快照无法证明数据未被玩家修改；首版不增加防作弊签名或服务器存档数据库。

### 保存时机与故障恢复

1. 新游戏初始化后保存完整快照。
2. 事件生成后先保存，再允许玩家选择。若保存失败，保留原存档及响应，提示重试保存，不进入后续步骤。
3. 选项结算使用确定性算术，返回包含历史、属性和阶段的新快照。浏览器保存成功后才提交到当前界面状态。
4. 第 14 次选择完成后先保存“待生成结局”；结局响应成功再保存“已结束”。
5. 页面刷新从快照恢复。生成中的状态恢复为可重试状态，不能把临时等待标志当作永久锁。
6. 服务重启后，浏览器重新发送完整快照即可继续；未返回或未保存的生成内容可能重做，但已保存的选择不会再次累计。
7. 遇到损坏或不支持版本的存档，保留原数据并提示无法读取，不静默清空或覆盖。

### 防止重复与过期响应

每个事件包含唯一标识，每份快照带修订号；应用检查该事件是否已经进入历史。相同快照和相同选择的结算应返回相同数值结果，不能在旧结果上再次累加。

前端在请求期间禁用重复操作，只接受与当前游戏标识、修订号及操作相符的响应；旧请求晚到不能覆盖更新存档。MVP 同一存档只支持一个活动游戏标签页，发现其他标签页改变存档时暂停本页操作并要求重新载入，不承诺多标签页并发游玩。

## 四、后端与本机、局域网运行

开发时使用 Vite 与 Express，前端使用相对 API 路径并由开发代理转发。交付运行时建议先构建前端，再由 Express 同时提供静态页面和 API，固定端口，减少跨域与访问源变化。

局域网运行需要监听局域网可达的网卡地址或 0.0.0.0，访问者使用服务器的局域网 IP；远端浏览器不能把 API 地址写成 localhost。监听和防火墙规则在实际启动阶段配置，本轮不改变电脑网络设置。

局域网访问的是本地 Web 服务，模型生成仍需要运行后端的电脑能够访问 DeepSeek API。API 密钥仅在后端环境变量中配置，不写入前端、存档或 Git。

React 与 TypeScript 的构建依据可参考 [Vite 文档](https://vite.dev/guide/)，API 与静态服务依据可参考 [Express 文档](https://expressjs.com/)。运行入口及实际端口在代码初始化后写入 README。

## 五、成员分工与协作边界

以下分工已由成员认领，每人负责一条明确的主线。

| 成员 | 主要职责 | 具体工作 | 交付标准 |
| --- | --- | --- | --- |
| 成员 A | 前端页面与交互 | 使用 React 实现开始页、日记事件页、结局页；展示事件、选项、精力、金钱和历史；隐藏学业与社交数值；处理等待、错误与重试状态 | 玩家能够完成开始、选择、查看结果和进入结局，过程界面符合日记式沉浸体验 |
| 成员 B | 后端接口与游戏规则 | 使用 Express 实现接口；定义公共数据结构；完成四维属性结算、14 天推进、A～D 分档、快照校验及重复提交处理 | 数值计算正确，完整四维状态不因前端隐藏而丢失，进度不重复推进，接口符合约定 |
| 成员 C | DeepSeek 接入与内容生成 | 编写心理治愈风格的事件和结局提示词；生成选项效果与结果描述；校验模型输出；处理调用异常；调整事件多样性和历史承接 | 事件符合当前属性与经历，效果不越界，文案回应新生期待与焦虑，结局包含标题、详情、评价与建议 |
| 成员 D | 存档恢复、整体集成与协作支持 | 实现 localStorage 存档、刷新恢复和过期响应处理；配置本机及局域网启动；组织完整流程验证；维护运行说明；协助其他成员处理阻塞 | 刷新及服务重启后可继续，局域网可访问，完整一局验收通过，跨模块问题得到跟踪 |

- **成员 B 牵头接口约定**：先与成员 A、C、D 对齐事件、选项、快照和结局结构，避免各自生成不兼容的代码。
- **成员 A 与成员 D 配合**：成员 A 负责页面状态展示，成员 D 提供保存、恢复和请求结果接纳能力。
- **成员 B 与成员 C 配合**：成员 B 管确定性的规则和算术，成员 C 管模型请求、提示词及生成内容校验。
- **成员 D 组织联调并提供协作支持**：各模块负责人修复所属问题，遇到阻塞时由成员 D 协调或协助处理。
- **每位成员维护个人开发记录**：文档统一放在 `docs/`，至少记录当前任务、接口依赖、完成情况、待协作事项和重要决策。格式见 [成员开发记录说明](成员开发记录说明.md)。

## 六、验收与开发顺序

| 验收项 | 通过条件 |
| --- | --- |
| 完整进程 | 从初始状态完成 14 次选择，无第 15 个事件；等待和重试不跳天 |
| 属性结算 | 四维按选项效果精确增减，保留负数，不自动恢复或扣费 |
| 分档 | 四个属性分别判定；阈值及相邻值覆盖无遗漏 |
| AI 输出 | 事件字段与选项效果完整；结局包含标题、详情、评价和建议 |
| 多样性与承接 | 对比不同属性及不同历史，至少两组后续情境存在可解释差异 |
| 展示规则 | 过程中只显示精力和金钱；选择前不泄露效果；结算文案能间接表达隐藏属性变化 |
| 内容风格 | 事件与结局以心理治愈和真实共情为主，能同时表达期待与焦虑 |
| 刷新恢复 | 待选择、已结算、待结局及已结束均恢复到正确阶段 |
| 服务重启 | 同一访问源重启 Express 后，原浏览器仍能继续已保存游戏 |
| 重试与重复提交 | 无重复加分；过期响应不覆盖新状态；结局失败不重做第 14 天 |
| 本机与局域网 | 本机及至少一台局域网设备完成事件生成与结算，各自保存进度 |
| 存储异常 | 写入失败或存档损坏时保留原数据并提示，不假装保存成功 |

已确认的 5 天共同开发节奏如下，各成员按上述职责协作完成当天目标：

| 时间 | 当天重点 | 完成标志 |
| --- | --- | --- |
| 第 1 天 | 初始化技术栈、规则和接口，固定事件走通流程，验证真实 API | 页面可选择并结算，模型成功返回结构化事件 |
| 第 2 天 | 接入合并事件生成、localStorage 与恢复 | 真实事件可连续游玩，刷新后继续 |
| 第 3 天 | 14 天进程、四维分档与 AI 结局、历史上下文 | 完整一局可结束并保存结局 |
| 第 4 天 | 服务重启、异常与重复操作、数值和内容验证 | 核心验收通过，本机与局域网可用 |
| 第 5 天 | 修复问题、回归、构建与启动说明 | 可运行的 MVP 与可复现的启动步骤 |
