# CampusMock

一个简易的、事件驱动的大学新生生活 AI 模拟器。围绕 AI 黑客松主题“你好，我的大学”，让玩家在网页中预演入学两周的校园生活，体验新生的期待、焦虑，以及不同选择带来的变化。

> 当前处于需求与文档规划阶段，尚未编写业务代码。已确认需求与待选实现方案在文档中分别标明。

## 已确认的项目约束

- **团队与周期**：4 人、5 天，以 Vibe Coding 为主，交付可演示的 MVP。
- **比赛方向**：主题为“你好，我的大学”，评分聚焦 AI 对新生期待与焦虑的预演。
- **单局范围**：模拟 14 天，每天 1 个事件，共 14 个事件；原则上不限制现实游玩时长。
- **四维初始值**：学业 0、社交 0、精力 7、金钱 1000。
- **属性变化**：由事件选择决定增减，部分选项影响精力和金钱；不额外设置每日自动恢复或固定扣费。
- **结局方式**：两周事件完成后，四个属性分别按数值大小及正负划分 A、B、C、D 档，再由大模型根据四个档位生成结局标题、详情、评价与建议。
- **核心 AI 亮点**：根据当前游戏天数与玩家属性生成不同事件，并让已有选择影响后续剧情。
- **运行范围**：MVP 仅需支持 localhost 和局域网访问，不要求公网部署。
- **存档要求**：页面刷新或服务重启后可恢复；倾向以浏览器 localStorage 保存少量文字存档。
- **API 预算**：主要用于测试和演示，用量较少，暂未指定金额上限。
- **成员分工**：已确认按前端交互、后端规则、AI 生成、存档与集成分为四块，使用成员 A～D 作为代号。
- **当前工作范围**：继续完善文档，不编写代码；演示时长暂不讨论。

## 核心玩法

1. **开始生活**：以学业 0、社交 0、精力 7、金钱 1000 开始第 1 天。
2. **生成事件**：后端调用大模型，结合天数、当前属性及过往选择生成事件。
3. **做出选择**：阅读标题、详情与选项，选择一次行动。
4. **结算变化**：应用模型量化、经过校验并已固定的选项属性增减，保存结果。
5. **继续下一天**：读完结果后推进，每天只结算 1 个事件；等待和重试不推进天数。
6. **生成结局**：第 14 个事件结算后，分别确定四维档位，再由大模型生成结局内容。

属性允许出现负数，负值不提前结束两周体验。已确认采用较宽松分档与较小单次波动，具体阈值和增减范围见游戏规则。

## 首版功能范围

- 开始游戏、14 天事件推进和四维属性展示。
- AI 随机事件、选项及属性变化量化。
- 保存过往事件与选择，使后续生成能够承接已有经历。
- 四维 A～D 分档及 AI 结局标题、详情、评价、建议。
- 浏览器存档、刷新与服务重启后的恢复。
- 生成等待、失败重试，以及防止重复结算。
- localhost 和局域网内的 Web 访问。

首版不包含账号、云端跨设备存档、多人联机、复杂地图、额外支线回合、语音或图片生成。以上首版功能范围与数值规则已冻结，后续如需调整再明确记录。

## AI 职责

| 调用场景 | 输入重点 | 生成内容 |
| --- | --- | --- |
| 随机事件生成 | 当前天数、四维属性、过往事件与选择 | 标题、详情、选项；相同天数下不同属性可产生不同事件 |
| 选项结果量化 | 事件情境、选项含义与数值约束 | 每个选项对应的学业、社交、精力、金钱增减 |
| 结局生成 | 四维最终值及各自的 A～D 档位，辅以本局经历 | 结局标题、详情、评价与建议 |

已确认合并生成事件、选项、属性变化及简短结果描述，选择后直接结算。正常一局为 14 次事件调用加 1 次结局调用，共约 15 次，不含重试。前两项不能退化为纯固定事件库；后端负责数据校验、确定性算术与进度，四维档位阈值由规则定义，大模型负责综合档位形成具体结局。

## 技术选型

| 模块 | 方案与状态 |
| --- | --- |
| 前端 | 已确认：React + Vite + TypeScript |
| 后端 | 已确认：Node.js + Express + TypeScript |
| 大模型 | 倾向 DeepSeek；具体模型与耗时、用量待实测 |
| 存档 | 倾向 localStorage；建议保存完整快照，后端不依赖持久游戏会话 |
| 运行方式 | 本机与局域网；建议 Express 提供构建后的前端和 API，使用固定访问端口 |

localStorage 的恢复范围是同一浏览器、同一访问源（协议、主机、端口）。切换 localhost 与局域网 IP、端口、浏览器或设备不会自动共享存档；清除站点数据会删除存档。[localStorage 说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

## 成员分工

| 成员 | 主要职责 | 核心交付 |
| --- | --- | --- |
| 成员 A | 前端页面与交互 | 开始页、游戏页、结局页；事件、属性与历史展示；等待、错误和重试状态 |
| 成员 B | 后端接口与游戏规则 | Express 接口、公共数据结构、属性结算、14 天推进、A～D 分档、快照校验与重复提交处理 |
| 成员 C | DeepSeek 接入与内容生成 | 事件与结局提示词、选项效果及结果描述、模型输出校验、调用异常处理、多样性与历史承接 |
| 成员 D | 存档恢复与整体集成 | localStorage、刷新恢复、过期响应处理、本机与局域网启动、完整流程验证及运行说明 |

成员 B 牵头接口约定，成员 D 组织联调，各模块负责人修复所属问题。A 与 D 对齐页面状态和存档能力，B 与 C 对齐游戏规则和模型生成边界。详细职责与验收标准见开发规划。

共同开发节奏：第 1 天对齐接口并建立最小可运行版本，第 2 天接通事件、结算和存档，第 3 天跑通完整 14 天与 AI 结局，第 4 天验证异常、数值边界及局域网访问，第 5 天修复、回归并完善启动说明。
